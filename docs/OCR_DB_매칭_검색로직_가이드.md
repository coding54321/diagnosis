# OCR → DB 매칭 검색 로직 가이드

OCR로 읽어온 데이터를 DB에 있는 유사 정보와 매칭할 때 쓰는 검색/매칭 설계 패턴 정리.

---

## 1. 전처리·정규화 (Preprocessing)

OCR 결과는 오타·공백·특수문자 차이가 있으므로, **검색 전에 쿼리와 DB 필드를 같은 규칙으로 정규화**하는 게 기본이다.

| 항목 | 예시 | 처리 |
|------|------|------|
| 공백 | `"블루 핸즈  강남"` | `trim()`, `replace(/\s+/g, ' ')` |
| 특수문자 | `(주)블루핸즈` | 검색용 필드에서는 제거 또는 통일 |
| 대소문자 | 영문 상호 | 비교 시 `toLowerCase()` (한글은 불필요) |
| 길이 | 1글자 토큰 | 보통 2글자 이상만 검색에 사용 (노이즈 제거) |

**현재 코드**: `national-repair-shops.ts`의 `preprocessQuery`, `generateShortTokens`에서 특수문자 제거·토큰 분리·2~3글자 prefix 추출로 OCR 오타를 완화하고 있음.

---

## 2. 신뢰도별 필드 우선순위

OCR 품질은 필드마다 다르다. **오류가 적고 구조화된 필드를 우선** 쓰는 게 일반적이다.

- **주소**: 도로명/지번은 형식이 비슷해 OCR 오류가 상대적으로 적고, DB와 토큰 단위 매칭이 잘 맞음. → **주소 우선 검색**이 합리적.
- **업체명/상호**: 손글씨·폰트·해상도에 따라 오인식(예: 블루핸즈 → 화북절)이 많음. → 주소로 후보를 좁힌 뒤 **이름으로 재정렬**하는 방식이 안정적.

**현재 코드**: `/api/shops`에서 `address`가 있으면 `searchNationalRepairShopsByAddress`로 먼저 검색하고, `q`(정비소명)가 있으면 그 결과를 정비소명 키워드로 재정렬(`address+name`)하고 있음.

---

## 3. 단계별 검색 파이프라인 (Staged Search)

한 번에 완벽 매칭을 노리기보다 **여러 단계를 거쳐 후보를 좁히고, 점수로 순위를 매기는** 방식이 많이 쓰인다.

```
[Stage 1] 넓게 후보 수집 (DB 부하 고려)
    → ILIKE / LIKE / 토큰 OR 조건으로 후보 N건
[Stage 2] 좁게 정렬·필터 (애플리케이션 또는 DB)
    → 유사도 점수 계산 → 상위 K건만 반환
[Stage 3] 폴백
    → 결과 없으면 검색어 완화(첫 단어만, 짧은 토큰만) 또는 다른 소스(CSV 등)
```

**현재 코드**:
- **정비소명**: `searchNationalRepairShops` 내부에서 ILIKE로 후보 조회 → Fuse.js로 유사도 정렬.
- **주소**: `searchNationalRepairShopsByAddress`에서 주소 토큰으로 `rdnmadr`/`lnmadr` ILIKE → 토큰 매칭 비율로 점수 계산 후 정렬.
- **폴백**: 이름 검색 실패 시 첫 단어만 재검색; 전국 DB 실패 시 `bluehands_seoul.csv` 사용.

---

## 4. 유사도·점수 설계

OCR–DB 매칭에서는 **한 가지 지표보다 여러 신호를 조합**하는 경우가 많다.

| 방식 | 장점 | 단점 |
|------|------|------|
| **정확 일치** | 단순, 오매칭 적음 | OCR 오타에 취약 |
| **토큰 포함률** | 오타·순서 변경에 강함 | 짧은 단어에 민감 |
| **편집 거리 (Levenshtein)** | 오타 개수 반영 | 비용·인덱스 지원 필요 |
| **N-gram (trigram)** | 부분 일치에 강함 | DB에 pg_trgm 등 필요 |
| **Fuse.js / fuzzy 라이브러리** | 가중치·임계값 조정 용이 | 메모리 상 후보 필요 |

**현재 코드**:
- **이름**: Fuse.js `threshold: 0.6`, `keys`에 업체명(0.7), 주소(0.2), 시군구(0.1) 가중치.
- **주소**: 토큰이 DB 주소에 포함된 비율(`matchCount / addressTokens.length`)로 점수, 0.3 이상만 사용.
- **이름+주소**: 주소 점수 + 정비소명 키워드 매칭 시 0.3 보너스.

---

## 5. 주소 매칭 시 유의점

- **토큰 분리**: 공백/특수문자 제거 후 `split(/\s+/)`, 2글자 이상만 사용하면 “서울 강남구 역삼동” 같은 조합에 유리.
- **도로명 vs 지번**: 둘 다 쿼리하거나, 한쪽만 있어도 매칭되도록 `rdnmadr`/`lnmadr` 모두 조건에 넣는 방식이 안전.
- **시군구 추출**: 표준 데이터에 시군구 컬럼이 없으면 주소 문자열에서 “~구”, “~시”, “~군” 패턴으로 추정해 표시/가중치에 활용 가능.

**현재 코드**: `searchNationalRepairShopsByAddress`에서 주소를 한글·숫자·공백 위주로 정제한 뒤 토큰으로 나누고, `rdnmadr`/`lnmadr`에 대해 `ilike.%토큰%` OR 조건으로 검색한 뒤, 토큰 매칭 비율로 정렬하고 있음.

---

## 6. 정비소명(상호) 매칭 시 유의점

- **키워드 추출**: 전체 문자열 일치 대신, 단어 단위로 잘라 2~3글자 prefix를 쓰면 “블루핸즈강남점” vs “블루핸즈 강남점”, “화북절 기아오토류” 같은 오인식에 강해짐.
- **불용어/접미사**: “(주)”, “주식회사”, “점” 등은 매칭에서 제거하거나 가중치를 낮추는 선택이 가능.
- **첫 단어 폴백**: 공백이 있는 검색어에서 결과가 없으면 첫 단어만으로 한 번 더 검색하면, 긴 상호가 잘린 경우에 도움이 됨.

**현재 코드**: `extractNameKeywords` / `generateShortTokens`로 2~3글자 키워드 생성, 이름 검색 실패 시 `q.split(/\s+/)[0]`으로 재검색.

---

## 7. 자동 선택 정책 (UI 쪽)

API가 여러 후보를 돌려줄 때 **어떤 것을 “선택된 정비소”로 볼지**를 정책으로 정해 두는 게 좋다.

- **1건만 반환**: 가장 유사한 1건만 반환하고, 클라이언트는 그대로 표시. (현재: `shops[0].업체명` 사용)
- **N건 반환 + 클라이언트 선택**: 상위 N건을 리스트로 보여주고 사용자가 고르게 하거나, 1위가 임계점 이상일 때만 자동 선택하고 아니면 “직접 선택” 유도.

**현재 코드**: 견적서 확인 페이지에서 `shops.length >= 1`이면 무조건 `shops[0].업체명`을 선택. 점수 임계값(예: 0.8 이상일 때만 자동 선택)을 두면 오매칭을 줄일 수 있음.

---

## 8. 요약: “OCR → DB 유사 매칭”에서 쓸 만한 순서

1. **전처리**: 쿼리·DB 비교 필드 정규화(공백, 특수문자, 토큰 길이).
2. **신뢰도 높은 필드 우선**: 주소 있으면 주소로 1차 검색, 이름은 재정렬/보조에 사용.
3. **2단계 검색**: 넓게 후보 수집(ILIKE/토큰) → 유사도 점수로 정렬 후 상위만 반환.
4. **점수 조합**: 주소 매칭률 + 이름 매칭(키워드/Fuse 등)을 합산하거나 가중 평균.
5. **폴백**: 검색어 완화(첫 단어, 짧은 토큰), 다른 데이터 소스(CSV 등).
6. **자동 선택**: 1위만 쓰는지, N건 중 사용자 선택인지, 점수 임계값이 있는지 정책으로 정하기.

이 순서는 지금 정비소 검색 로직과 같은 방향이며, 필요하면 단계별로 임계값·가중치·폴백만 조정하면 된다.
