# 전국자동차정비업체 표준데이터 API 연동 구상

## 1. 목표

- 견적서 입력(사진/업로드/직접입력) 시 **인식된 정비소 정보**(업체명, 주소 등)로 **전국자동차정비업체 표준데이터**와 매칭해 표시.
- 인식되지 않으면 **빈칸**으로 두고, 사용자가 **검색**해서 정비소를 찾을 수 있게 함.

---

## 2. API 개요 (공공데이터포털)

| 항목 | 내용 |
|------|------|
| **요청 주소** | `http://api.data.go.kr/openapi/tn_pubr_public_auto_maintenance_company_api` |
| **제공 범위** | 자동차관리법에 따라 지자체가 발급한 자동차정비업체 등록 정보 |
| **갱신 주기** | 반기 |
| **트래픽** | 개발 1,000회/일, 운영은 활용사례 등록 시 증가 신청 가능 |

**요청 파라미터 (검색/필터용)**  
`pageNo`, `numOfRows`, `type`(xml/json), `inspofcNm`, `inspofcType`, `rdnmadr`, `lnmadr`, `phoneNumber`, `bsnSttus` 등.

**응답 필드 (주요)**  
`inspofcNm`(업체명), `inspofcType`(업체종류), `rdnmadr`(도로명주소), `lnmadr`(지번주소), `latitude`, `longitude`, `phoneNumber`, `bsnSttus`(영업상태), `referenceDate` 등.

---

## 3. 데이터 소스 전략: API 직접 호출 vs DB 적재

### 옵션 A: 요청 시마다 API 호출

- **장점**: 구현 단순, 데이터 항상 최신.
- **단점**:
  - 개발 트래픽 1,000회/일 제한 → 견적 확인·검색이 많아지면 쉽게 소진.
  - 요청마다 지연, 페이지네이션 처리 필요.
  - 공공 API 장애 시 우리 서비스 검색 전부 영향.

### 옵션 B: 전체 데이터 DB 적재 후 조회 (권장)

- **장점**:
  - 트래픽 제한과 무관하게 **검색/노출** 가능.
  - DB 인덱스로 **빠른 검색** (업체명, 주소 등).
  - 공공 API 장애 시에도 **검색·표시**는 유지.
- **단점**:
  - 최초 수집·반기 갱신용 **동기화 로직** 필요.
  - 저장 공간·스키마 설계 필요 (규모는 수만 건 수준으로 관리 가능).

**권장**: **옵션 B (DB 적재)**  
- 일 1,000회 제한을 고려하면, 견적서 확인·검색을 매번 API로 쓰기엔 부담이 큼.  
- 반기 갱신이므로, 주기적으로 전체를 받아 DB를 갱신하는 방식이 적합함.

## 4. DB 설계 (Supabase)

### 4.1 테이블: `national_repair_shops` (가칭)

| 컬럼 | 타입 | 설명 |
|------|------|------|
| `id` | uuid | PK (default gen_random_uuid()) |
| `inspofc_nm` | text | 자동차정비업체명 |
| `inspofc_type` | text | 업체종류 |
| `rdnmadr` | text | 소재지 도로명주소 |
| `lnmadr` | text | 소재지 지번주소 |
| `latitude` | numeric | 위도 |
| `longitude` | numeric | 경도 |
| `phone_number` | text | 전화번호 |
| `bsn_sttus` | text | 영업상태 |
| `reference_date` | date | 데이터기준일자 |
| `instt_code` | text | 제공기관코드 (선택) |
| `created_at` | timestamptz | 최초 적재 시각 |
| `updated_at` | timestamptz | 마지막 동기화 시각 |

- **인덱스**: `inspofc_nm`, `rdnmadr`, `lnmadr` (검색용, 필요 시 GIN/trgm 등).
- **RLS**: 읽기만 허용 (anon/인증 사용자 SELECT), 쓰기는 서버/관리만.

### 4.2 견적서와의 연결

- **현재**: `estimates.shop_name` (문자열만 저장).
- **유지**: 화면/저장은 계속 `shop_name`(문자열)로 두고, “어떤 표준 업체를 선택했는지”만 추가할지 선택 가능.
- **선택 확장**: 나중에 `estimates.national_shop_id` (FK to `national_repair_shops.id`)를 두면 “표준데이터 기준 정비소”로 통계·검증에 활용 가능. 구상 단계에서는 **검색 결과에서 선택한 업체명을 `shop_name`에 넣는 것**만 해도 충분.

---

## 5. 데이터 동기화 (전체 데이터 적재)

- **주기**: API 갱신 주기(반기)에 맞춰 **반기 1회** 또는 수동 실행.
- **방식**:
  1. `pageNo=1`, `numOfRows=1000`(최대 허용값 확인)으로 요청.
  2. 응답이 있으면 `national_repair_shops`에 **upsert** (예: `inspofc_nm` + `rdnmadr` + `instt_code` 등으로 유니크 판단 후 insert/update).
  3. `totalCount` 등이 있으면 마지막 페이지까지 반복.
- **구현 위치**:  
  - **스크립트** 예: `scripts/sync-national-repair-shops.ts` (또는 `.js`)  
  - 환경변수: `DATA_GO_KR_SERVICE_KEY` (공공 API 서비스키).  
  - 로컬/CI에서 실행 후 Supabase에 반영.
- **운영**: Cron(서버) 또는 GitHub Actions 등으로 반기마다 실행하거나, “관리자 동기화” 버튼으로 수동 실행.

## 6. 검색 API (우리 서비스)

- **역할**: Review 화면의 “정비소 검색” 및 “OCR 인식값으로 업체 찾기”에 사용.
- **인터페이스**: 기존 `/api/shops?q=검색어` 유지하고, **백엔드만** 전국 표준데이터 DB 조회로 전환(또는 병행).

### 6.1 검색 조건

- **쿼리 파라미터**: `q` (업체명·주소 일부 등).
- **DB 조회**:  
  - `inspofc_nm` ILIKE `%q%`  
  - OR `rdnmadr` ILIKE `%q%`  
  - OR `lnmadr` ILIKE `%q%`  
  - (선택) `phone_number` 일부 매칭.
- **필터**: `bsn_sttus = '영업'` (또는 null) 등 필요 시 적용.
- **정렬**: 업체명 기준, 또는 매칭 점수(업체명 정확도 우선) 등.
- **제한**: 예) 50건.

### 6.2 응답 형식 (기존 UI 호환)

현재 Review는 `BluehandsShop` 형태(`업체명`, `시군구`, `주소`)를 기대하므로, **같은 형태로 매핑**하면 UI 변경을 최소화할 수 있음.

```ts
// 예: API 응답 타입 (기존 BluehandsShop 대체용)
interface NationalRepairShopDisplay {
  업체명: string;      // inspofc_nm
  시군구: string;     // rdnmadr 또는 lnmadr에서 추출 (또는 별도 컬럼 없으면 "주소 앞부분")
  주소: string;       // rdnmadr || lnmadr
  전화번호?: string;  // phone_number (선택)
  // 기존 BluehandsShop과 동일 키로 맞추면 setShopName(shop.업체명) 등 그대로 사용 가능
}
```

- 시군구는 주소 문자열에서 파싱하거나, “도로명주소 앞 2단어” 등으로 대체 가능. (표준데이터에 시군구 필드가 없으면)

## 7. 유저 플로우 (Review 페이지)

### 7.1 OCR/입력으로 정비소 정보가 있을 때

1. 견적서 인식 결과에 `shopName`(또는 주소 등)이 있으면 **그 값을 검색어로** 전국 표준데이터 검색 API 호출.
2. **1건 이상 매칭**:
   - 첫 번째 항목을 “자동 선택” 후 `shopName`에 `inspofc_nm` 표시하거나,
   - “추천: ○○정비”처럼 1건만 보여주고 사용자가 확인/수정 가능하게 할 수 있음.
3. **0건**:  
   - `shopName`은 OCR 값 그대로 두거나 빈칸으로 두고,  
   - “정비소 검색”으로 사용자가 직접 검색해 선택.

### 7.2 정비소 정보가 없을 때

- `shopName`은 **빈칸**.
- 사용자가 “정비소” 탭 → 검색창에 업체명·주소 입력 → 위 검색 API로 목록 표시 → 하나 선택 시 `shopName`(및 필요 시 주소 등) 설정.

### 7.3 직접 입력(Manual) 유입

- 현재처럼 `shopName: '직접 입력'` 또는 빈칸으로 두고, 정비소 탭에서만 “전국 표준데이터 검색”을 쓰게 할 수 있음.

## 8. 구현 순서 제안

1. **공공 API 키 발급**  
   - 공공데이터포털에서 “전국자동차정비업체 표준데이터” 활용 신청 후 서비스키 발급.

2. **DB**  
   - Supabase에 `national_repair_shops` 테이블 + 인덱스 생성.  
   - (선택) RLS로 읽기 전용 정책 설정.

3. **동기화 스크립트**  
   - 페이지네이션으로 전체 데이터 요청 → Supabase upsert.  
   - 1회 수동 실행으로 최초 적재.

4. **검색 API**  
   - `/api/shops`를 DB 조회 기반으로 변경(또는 전국 데이터 우선, 없으면 기존 블루핸즈 CSV fallback).  
   - 응답을 `업체명`, `시군구`, `주소` 등 기존 UI 호환 형태로 매핑.

5. **Review 페이지**  
   - OCR 결과 `shopName`/주소가 있으면 마운트 시 한 번 검색 API 호출 → 추천 1건 표시 또는 자동 선택.  
   - 없으면 빈칸, “정비소 검색”은 기존처럼 검색창 + 목록 선택.  
   - 목록 클릭 시 `setShopName(shop.업체명)` 유지(표준데이터의 `inspofc_nm` 사용).

6. **운영**  
   - 반기마다 동기화 스크립트 실행(또는 관리자 실행)으로 DB 갱신.

---

## 9. 정리

- **데이터 소스**: 전국자동차정비업체 표준데이터는 **한 번(또는 반기마다) API로 받아 DB에 넣고**, 검색은 **DB만 사용**하는 방식이 트래픽·속도·안정성 측면에서 유리함.
- **UI/저장**: 기존 “정비소 이름 하나(문자열)” 흐름을 유지하면서, 검색 결과만 **표준데이터**로 바꾸면 됨.
- **인식 실패 시**: 정비소는 빈칸으로 두고, 사용자가 “정비소 검색”으로 찾아 선택하게 하면 됨.

이 구상대로 진행하면, “정비소 데이터를 전국 표준데이터 API로 확장하고, 인식값으로 찾고 못 찾으면 검색” 요구사항을 만족할 수 있다.
