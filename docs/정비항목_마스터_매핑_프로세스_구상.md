# 정비항목 마스터 테이블 채택 및 매핑 프로세스 구상

## 1. 개요

- **마스터 테이블**: `public/bluehands_jobs_normalized_v4.csv` 를 서비스의 **정비항목 마스터**로 채택한다.
- **목표**: 견적서 OCR → 사용자 확인·확정 → **확정된 정비항목을 마스터 항목 중 하나에 매핑**하여, 이후 가격 비교·검증·통계를 마스터 기준으로 일관되게 수행한다.

---

## 2. 마스터 테이블 구조 (v4 CSV)

| 컬럼 | 설명 | 비고 |
|------|------|------|
| `job_id` | 고유 ID (예: BH_0001) | **매핑 결과로 저장할 식별자** |
| `job_name_raw` | 원문 작업명 | 수집 원본 |
| `job_name_norm` | 정규화된 작업명 | 매칭·검색에 사용 |
| `system_type` | 시스템 구분 (ENGINE, BRAKE, BODY 등) | 필터/분류 |
| `area` | 영역 (ENGINE_BAY, REAR 등) | 필터/분류 |
| `component_group` | 부품 그룹 (RADIATOR, BRAKE_PAD 등) | 필터/분류 |
| `position_side` | 좌/우/양쪽 (LH, RH, BOTH, N/A) | 필터/분류 |
| `axle_or_row` | 축/열 (FRONT_AXLE, REAR_AXLE 등) | 필터/분류 |
| `quantity_type` | 수량 유형 (1EA, BOTH_SIDE 등) | 필터/분류 |
| `work_type` | 작업 유형 (REPLACE, ADJUST, PAINT 등) | 필터/분류 |
| `labor_category` | 공임 카테고리 (FUNCTIONAL, MAINTENANCE, BODY_PAINT 등) | 검증/통계 |

- 약 161개 항목 (BH_0001 ~ BH_0160).

## 3. 전체 프로세스 흐름

```
[견적서 이미지/텍스트]
        │
        ▼
┌───────────────────┐
│  OCR 분석         │  ← 기존: analyzeEstimateImage / analyzeEstimateFromText
│  - name (원문)     │
│  - normalizedName │  ← AI가 추론한 표준 작업명 (참고용, 마스터와 무관)
│  - part/labor/총액 │
└─────────┬─────────┘
          │
          ▼
┌───────────────────┐
│  사용자 확인      │  ← 기존 Step 4: 견적 내역 확인
│  - 항목명/금액 수정│
│  - 누락 추가      │
│  - 삭제            │
└─────────┬─────────┘
          │
          ▼
┌───────────────────┐
│  사용자 확정      │  ← "다음" 또는 "검증하기" 클릭 시
│  (항목 리스트 확정)│
└─────────┬─────────┘
          │
          ▼
┌───────────────────────────────────────────┐
│  마스터 매핑 단계 (신규)                    │
│  각 확정 항목 → 마스터 job_id 1개 선택     │
│  - 자동 제안: job_name_norm 유사도/키워드  │
│  - 사용자 선택: 드롭다운/검색으로 변경 가능 │
│  - "마스터에 없음": 매핑 생략 또는 나중 처리 │
└─────────┬─────────────────────────────────┘
          │
          ▼
┌───────────────────┐
│  저장 & 검증      │  ← item에 master_job_id 포함 저장
│  - WPC/FRT 조회 시 │     → job_id 기준으로 가격 비교
│    job_id 사용    │
└───────────────────┘
```

## 4. 매핑 단계 상세 설계

### 4.1 언제 매핑을 수행할지

- **옵션 A**: 사용자가 견적 내역 확인 후 "다음"을 눌렀을 때, **항목별 마스터 매핑 화면**을 한 단계 추가한다. (Step 4.5)
- **옵션 B**: Step 4(견적 확인) 화면에서 **항목별로 인라인**으로 "마스터 항목 선택" 드롭다운을 둔다. 확정 시 함께 저장.
- **옵션 C**: Step 4에서 확정만 하고, **검증 결과 화면**에서 매핑이 안 된 항목만 "마스터 선택" 유도.

**권장**: **옵션 A**  
- 견적 확인(금액/항목명)과 “어떤 마스터에 매칭할지”를 단계를 나누면 인지 부하가 줄고,  
- “확정된 항목 N개 → 각각 마스터 1개 선택”이 한 화면에 모여 있어 일괄 처리·검증하기 좋다.

### 4.2 자동 매칭(제안) 로직

- **입력**: 사용자가 확정한 항목의 `name`(원문) 또는 (있다면) `normalizedName`.
- **출력**: 마스터 행 1개를 **1순위 후보**로 제안. 필요 시 상위 3~5개를 후보 리스트로 제공.

**방식**:

1. **정규화 문자열 매칭**  
   - `job_name_norm`과 확정 항목명을 공백/괄호 제거, 소문자 등으로 정규화 후  
   - 완전 일치 → 우선 제안  
   - 포함 관계(한쪽이 다른 쪽을 포함) → 다음 후보

2. **유사도 기반**  
   - 정규화된 문자열 간 레벤시테인 거리, 또는 코사인 유사도(토큰/n-gram)로 점수 부여  
   - 점수 상위 1개를 기본 제안, 상위 N개를 선택지로 노출

3. **키워드/메타데이터 보조**  
   - `system_type`, `work_type`, `labor_category` 등이 견적 항목의 카테고리와 맞으면 가산  
   - (현재 `category`는 엔진/제동/변속기 등이므로, 마스터의 `system_type`과 대응 테이블을 두면 됨)

구현 시에는  
- 먼저 **1번(정규화 + 완전/부분 일치)**만으로도 상당수 자동 매칭 가능.  
- 부족하면 **2번(유사도)** 추가.  
- 3번은 선택(정확도 개선용).

### 4.3 사용자 선택 UI

- 각 확정 항목에 대해:
  - **제안된 마스터 1개**를 기본 선택된 상태로 표시 (예: `BH_0057 엔진 오일 / 필터`).
  - **드롭다운 또는 검색 가능한 선택기**로 변경 가능:
    - `job_id + job_name_norm` 리스트 (필터: system_type, work_type 등).
  - **"마스터에 없음"** 옵션:
    - 매핑 없이 저장 (검증 시 "비교 불가"로 표시하거나, 기존처럼 `normalizedName`/이름 기반 폴백).

### 4.4 저장 데이터 구조

- **EstimateItem** (또는 DB의 estimate_items)에 필드 추가:
  - `master_job_id: string | null`  
    - 예: `"BH_0057"`  
    - null이면 "마스터에 없음" 또는 미매핑.

- 검증/가격 비교 시:
  - `master_job_id`가 있으면 → **job_id 기준**으로 WPC·FRT·평균가 조회.
  - 없으면 → 기존처럼 `normalizedName` 또는 `name`으로 폴백(가능한 경우).

## 5. 기술 구현 포인트

### 5.1 마스터 데이터 로드

- **서버**: CSV를 빌드/시작 시 한 번 파싱해 메모리 캐시하거나, Supabase 등 DB에 테이블로 넣고 조회.
- **클라이언트**: 마스터 목록이 필요하면 API 라우트에서 JSON으로 반환 (예: `GET /api/maintenance-master`).
- **형식**: v4 CSV 컬럼 그대로 타입 정의.

```ts
// 예시 타입
interface MaintenanceMasterItem {
  job_id: string;
  job_name_raw: string;
  job_name_norm: string;
  system_type: string;
  area: string;
  component_group: string;
  position_side: string;
  axle_or_row: string;
  quantity_type: string;
  work_type: string;
  labor_category: string;
}
```

### 5.2 자동 매칭 API

- **입력**: `{ itemName: string, normalizedName?: string }` (확정된 항목 1개).
- **출력**: `{ suggested: MaintenanceMasterItem | null, candidates: MaintenanceMasterItem[] }`.
- 서버에서 마스터 목록 + 위 4.2 로직으로 1순위 제안 + 후보 리스트 반환.

### 5.3 OCR 단계와의 관계

- OCR에서 나오는 `normalizedName`은 **참고용**으로만 둔다.  
- 최종 매핑은 **사용자 확정 후, 마스터 매핑 단계**에서 사용자 선택 + 자동 제안으로 확정한다.  
- 필요하면 OCR 프롬프트에 “가능하면 v4 마스터의 job_name_norm에 가깝게 써라”는 힌트를 넣어 자동 제안 정확도를 보조할 수 있다.

### 5.4 DB/스키마 변경

- `estimate_items`(또는 견적 항목 저장 테이블)에 `master_job_id` (nullable string) 컬럼 추가.
- 이력/통계 조회 시 `master_job_id` 기준 집계 가능.

## 6. 단계별 적용 제안

| 단계 | 내용 |
|------|------|
| 1 | v4 CSV 파싱 모듈 + 타입 정의 + 메모리/API 로드 |
| 2 | 자동 매칭 함수 (정규화 + 완전/부분 일치 → 1순위 제안) |
| 3 | API: `GET /api/maintenance-master`, `POST /api/match-master` (또는 쿼리 파라미터로 항목명 전달) |
| 4 | UI: 확정 후 "마스터 매핑" 단계 추가 (항목별 제안 + 드롭다운/검색) |
| 5 | EstimateItem에 `master_job_id` 추가, 저장/조회 반영 |
| 6 | 검증 엔진: `master_job_id` 우선 사용, 없을 때 기존 name/normalizedName 폴백 |
| 7 | (선택) 유사도 기반 후보 확장, OCR 프롬프트에 job_name_norm 힌트 |

---

## 7. 요약

- **마스터**: `bluehands_jobs_normalized_v4.csv` → `job_id`를 정비항목의 표준 식별자로 사용.
- **프로세스**: 견적서 OCR → 사용자 확인·확정 → **항목별로 마스터 1개 매핑(자동 제안 + 사용자 선택)** → `master_job_id` 저장 → 검증/가격 비교는 job_id 기준.
- **효과**: 비교·통계가 마스터 기준으로 통일되고, 오인식/표기 차이는 사용자가 한 번만 매핑하면 이후에는 job_id로 일관 처리할 수 있다.

이 구상을 기준으로 단계 1부터 순서대로 구현하면 된다. 필요하면 특정 단계(예: 자동 매칭 식, UI 와이어프레임)만 더 구체화할 수 있다.
